# Proposed table dictionary

All tables use InnoDB/utf8mb4. Unless noted, primary key is BIGINT UNSIGNED `id`, timestamps are DATETIME(6). FKs match referenced types. Money = DECIMAL(19,4) with CHAR(3) currency, quantity = DECIMAL(18,3); no FLOAT/DOUBLE. Status fields are VARCHAR state vocabularies. Below are all proposed logical columns; audit/ledger rows are append-only.

### Column notation and defaults
- `id` means `BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY`; explicitly stated composite PKs replace it. An FK `*_id` is `BIGINT UNSIGNED` matching its referenced key unless stated otherwise.
- A column marked `NULL` is nullable; every other listed column is proposed `NOT NULL`. No database default is implied unless a `DEFAULT` is written. Any business default must be approved if it changes customer or financial behavior.
- Grouped names separated by `/` share the type and nullability immediately following the group (for example, `subtotal/total DECIMAL(19,4)`). `timestamps` means `created_at` and `updated_at` DATETIME(6); append-only tables may list only `created_at`.
- Abbreviated common fields use these proposed types: `status`, `state`, `resolution`, `channel`, `method`, `reason_code`, `event_type`, `source`, `condition`, `disposition`, `priority`, and `*_type` are VARCHAR(24) unless a specific size is stated; boolean `is_*`, `requires_shipping`, and `restock` fields are TINYINT(1); `sort_order` is INT; `position` is INT UNSIGNED; fields ending `_at` are DATETIME(6), `_date` are DATE, `_qty`/`quantity` are DECIMAL(18,3), and `notes`/`description` are TEXT unless a specific type/size is stated. Requester snapshots use name VARCHAR(160), email VARCHAR(190), and phone VARCHAR(32).
- These are design conventions, not generated DDL. Any field whose business meaning cannot be inferred is called out in `OPEN_DECISIONS.md`; do not infer enum values or business-sensitive defaults from these type conventions.

## Identity and access
- **users** (extend existing): id PK, name VARCHAR(160), email VARCHAR(190) UNIQUE, email_verified_at DATETIME(6) NULL, password VARCHAR(255), phone VARCHAR(32) NULL, preferred_locale VARCHAR(10) DEFAULT ar, is_active TINYINT(1), remember_token VARCHAR(100) NULL, created_at/updated_at, deleted_at NULL. Existing migration has name/email/email_verified_at/password/remember_token/timestamps.
- **customers**: id, user_id FK NULL UNIQUE, customer_number VARCHAR(40) UNIQUE, display_name VARCHAR(160), phone VARCHAR(32), email VARCHAR(190) NULL, marketing_consent_at DATETIME(6) NULL, notes TEXT NULL, timestamps, deleted_at DATETIME(6) NULL. Website checkout requires a linked active user; staff can create an unregistered customer for social orders. Soft deletion preserves order history.
- **roles**: id, code VARCHAR(80) UNIQUE, name VARCHAR(120), is_system TINYINT(1), timestamps. **permissions**: id, code VARCHAR(120) UNIQUE, description VARCHAR(255) NULL, timestamps.
- **user_role**: user_id FK, role_id FK, assigned_by FK users NULL, created_at; composite PK(user_id,role_id). **role_permission**: role_id FK, permission_id FK; composite PK(role_id,permission_id).
- **customer_addresses**: id, customer_id FK, label VARCHAR(80) NULL, recipient_name VARCHAR(160), phone VARCHAR(32), country_code CHAR(2), governorate/city VARCHAR(120), district VARCHAR(120) NULL, street VARCHAR(255), building/floor/apartment VARCHAR(80) NULL, landmark VARCHAR(255) NULL, postal_code VARCHAR(20) NULL, latitude/longitude DECIMAL(10,7) NULL, is_default TINYINT(1), timestamps, deleted_at NULL.

## Catalog and translations
- **categories**: id, parent_id self-FK NULL, slug VARCHAR(190) UNIQUE, image_path VARCHAR(500) NULL (public category artwork uploaded from the dashboard), sort_order INT, is_active, deleted_at, timestamps. **category_translations**: id, category_id FK, locale VARCHAR(10), name VARCHAR(190), description TEXT NULL, UNIQUE(category_id,locale). Existing categories remain valid with a NULL image path.
- **brands**: id, slug VARCHAR(190) UNIQUE, logo_path VARCHAR(500) NULL, is_active, deleted_at, timestamps. **brand_translations**: id, brand_id FK, locale, name, description NULL, UNIQUE(brand_id,locale).
- **products**: id, brand_id FK NULL, product_type VARCHAR(20) simple/variable, sku VARCHAR(80) UNIQUE, slug VARCHAR(190) UNIQUE, status VARCHAR(24), store_availability_status VARCHAR(20) (`available`,`unavailable`), availability_checked_at DATETIME(6) NULL, availability_checked_by FK users NULL, requires_shipping TINYINT(1), tax_class VARCHAR(80) NULL, weight_g INT UNSIGNED NULL, published_at NULL, deleted_at, timestamps. Staff manually controls product-level store availability; this is not stock quantity. The status applies to all variants of the product. **product_translations**: id, product_id FK, locale, name VARCHAR(220), short_description VARCHAR(500) NULL, description LONGTEXT NULL, meta_title VARCHAR(220) NULL, meta_description VARCHAR(500) NULL, UNIQUE(product_id,locale).
- **product_categories**: product_id/category_id FKs, is_primary TINYINT(1), composite PK. **product_variants**: id, product_id FK, sku VARCHAR(80) UNIQUE, barcode VARCHAR(80) NULL UNIQUE, variant_name VARCHAR(220) NULL, is_default/is_active TINYINT(1), current_regular_price DECIMAL(19,4), current_sale_price DECIMAL(19,4) NULL, currency CHAR(3) DEFAULT EGP, current_price_version_id FK product_price_history NULL, weight_g INT UNSIGNED NULL, deleted_at, timestamps. Prices are set per sellable variant (including size/color; a simple product has its default variant); a NULL sale price means no current product-level discount. Only users with administrator price-management permission may change prices. Product-level availability controls all variants. There is no owned-stock quantity or inventory ledger.
- **product_price_history** (append-only): id, product_variant_id FK, version_no INT UNSIGNED, factory_unit_cost/inbound_delivery_unit_cost/packaging_unit_cost/advertising_unit_cost DECIMAL(19,4), pricing_cost_total DECIMAL(19,4), profit_rate_percent DECIMAL(9,4), calculated_regular_price DECIMAL(19,4) NULL, official_regular_price DECIMAL(19,4), sale_price DECIMAL(19,4) NULL, currency CHAR(3), recorded_at DATETIME(6), recorded_by FK users, change_reason VARCHAR(255) NULL, UNIQUE(product_variant_id,version_no). Snapshot the initial price and every subsequent regular-price, discount, or cost-input change per variant. The four per-unit cost inputs sum exactly to `pricing_cost_total`. **Approved 2026-10-29:** `profit_rate_percent` is calculated as markup on cost: (official regular price − total per-unit cost) / total per-unit cost × 100, rounded half-up to four decimal places; losses may produce a negative percentage, while zero total cost is rejected because the percentage is undefined. The percentage is informational and never calculates or overrides the official regular price. Sale price does not drive this calculation. The first price version may have a null reason; a reason is required for later versions to explain an adjustment. Customer shipping is separate. Factory cost is a pricing input, not a purchase order, payable, or inventory valuation record. Discount scheduling is not defined; no automatic start/end behavior is implied. Public storefront rendering of both prices remains in S1-10.
- **product_collections**: id, code VARCHAR(80) UNIQUE (`new_arrivals`,`popular`, etc.), is_active TINYINT(1), sort_order INT, timestamps. **product_collection_translations**: id, product_collection_id FK, locale VARCHAR(10), title VARCHAR(160), UNIQUE(product_collection_id,locale).
- **product_collection_items**: id, product_collection_id/product_id FKs, position INT UNSIGNED, added_by FK users, added_at DATETIME(6), UNIQUE(product_collection_id,product_id), UNIQUE(product_collection_id,position). Staff curate membership and order manually; “new” does not mean latest created and “popular” does not mean auto-ranked sales.
- **product_availability_history** (append-only): id, product_id FK, availability_status VARCHAR(20) (`available`,`unavailable`), checked_at DATETIME(6), checked_by FK users, note VARCHAR(255) NULL, created_at. Record each manual change/check; it is not supplier stock quantity.
- **attributes**: id, code VARCHAR(80) UNIQUE, input_type VARCHAR(24), is_variant_axis TINYINT(1), sort_order INT, timestamps. **attribute_translations**: id, attribute_id FK, locale, name VARCHAR(120), UNIQUE(attribute_id,locale).
- **attribute_values**: id, attribute_id FK, code VARCHAR(100), sort_order INT, UNIQUE(attribute_id,code). **attribute_value_translations**: id, attribute_value_id FK, locale, value VARCHAR(160), UNIQUE(attribute_value_id,locale).
- **variant_attribute_values**: variant_id/attribute_id/attribute_value_id FKs, composite PK(variant_id,attribute_id), UNIQUE(variant_id,attribute_value_id). **product_images**: id, product_id FK, variant_id FK NULL, path VARCHAR(500), alt_text VARCHAR(255) NULL, sort_order INT, is_primary TINYINT(1), timestamps.

## Supplier directory
- **suppliers**: id, code VARCHAR(60) UNIQUE, supplier_type VARCHAR(20) (`factory`,`showroom`), name VARCHAR(190), owner_name VARCHAR(160) NULL, owner_phone VARCHAR(32) NULL, contact_name VARCHAR(160) NULL, email VARCHAR(190) NULL, phone VARCHAR(32) NULL, address_json JSON NULL, notes TEXT NULL, is_active TINYINT(1), timestamps, deleted_at DATETIME(6) NULL. Owner details are separate from the optional contact person and contact phone. Dashboard address inputs map ordinary fields (governorate/city/district/street/building/floor/landmark/postal code) into the JSON column; no asynchronous address lookup is required.
- **product_suppliers** (current supplier-product relationship): id, product_id/supplier_id FKs, supplier_product_code VARCHAR(100) NULL, unit_cost DECIMAL(19,4), currency CHAR(3), supplier_availability_status VARCHAR(20) (`available`,`unavailable`,`unknown`), valid_from/valid_until DATETIME(6) NULL, is_active TINYINT(1), updated_by FK users NULL, notes VARCHAR(255) NULL, timestamps; UNIQUE(product_id,supplier_id). S1-05 lets staff link the same product to several factories/showrooms and manually record cost, supplier availability and offer validity. This is not a purchase order or inventory record.
- **product_supplier_history** (append-only): id, product_supplier_id FK, version_no INT UNSIGNED, unit_cost DECIMAL(19,4), currency CHAR(3), supplier_availability_status VARCHAR(20), valid_from/valid_until DATETIME(6) NULL, is_active TINYINT(1), changed_at DATETIME(6), changed_by FK users NULL, change_reason VARCHAR(255) NULL, created_at; UNIQUE(product_supplier_id,version_no). S1-05 writes version 1 on link creation and a new version for each actual cost/availability/validity/active-state change; the dashboard shows actor and time. Preserve history; never rewrite or delete it.
- **order_item_supplier_selections** (append-only): id, order_item_id FK, order_revision_id FK, product_supplier_id FK, selected_supplier_id FK suppliers, supplier_name_snapshot VARCHAR(190), selected_unit_cost DECIMAL(19,4), currency CHAR(3), action VARCHAR(16) (`selected`,`replaced`,`cancelled`), selected_by FK users NULL, selected_at DATETIME(6), reason VARCHAR(255) NULL, created_at. Records which linked supplier was chosen for each ordered product line and the supplier cost used at that moment. Re-selection appends a row; never overwrite prior choice. Supplier choice is internal unless it changes customer-facing price/product/quantity, which requires a new approved order revision.

## Inventory
No inventory or warehouse tables are proposed. Variant availability is a manually managed storefront orderability flag based on checking the assigned supplier, not a claim of on-hand quantity. Customer return/damage records preserve condition and outcome but do not post stock movements.

Out of scope: order purchasing, sourcing requests, competing quote workflows, purchase orders, goods receipts, supplier returns/payables, warehouses, stock quantities, movements, and reservations. Supplier-product options and per-order selections are in scope; the actual procurement remains outside the system.

## Commerce
- **carts**: id, customer_id FK NULL, guest_token CHAR(36) UNIQUE NULL, status, currency CHAR(3), expires_at DATETIME(6) NULL, timestamps. Exactly one owner form (customer or guest token) is required. Guests can view checkout, but placing an order requires an authenticated customer; attach/merge the guest cart transactionally after login/registration, preserving all variants and quantities, then restore checkout. If an account cart exists, merge duplicate variant quantities without dropping distinct selections and validate before placement. **cart_items**: id, cart_id/variant_id FKs, quantity DECIMAL(18,3), added_at/updated_at, UNIQUE(cart_id,variant_id); cart price is non-authoritative and must be refreshed from active price history at checkout.
- **customer_favorites**: id, customer_id FK, product_id FK, created_at, UNIQUE(customer_id,product_id). Approved simple Favorites feature: one heart toggle/list per customer, saving the product rather than a selected size/color variant. No named lists, quantities, sharing, or full Wishlist behavior.
- **orders**: id, order_number VARCHAR(40) UNIQUE, public_id CHAR(36) UNIQUE, customer_id FK, channel VARCHAR(20) (`website`,`facebook`,`instagram`), created_by_user_id FK users NULL, source_reference VARCHAR(120) NULL, status VARCHAR(24), closed_at DATETIME(6) NULL, close_outcome VARCHAR(16) NULL (`success`,`failure`), closure_reason_code VARCHAR(80) NULL, currency CHAR(3) DEFAULT EGP, subtotal/discount_total/customer_shipping_charge/tax_total/grand_total DECIMAL(19,4), applied_revision_id FK order_revisions NULL, customer_note TEXT NULL, placed_at DATETIME(6), cancelled_at NULL, timestamps. Website creator is the authenticated customer user; social creator is the staff member. Monetary fields project applied immutable revision; payment/shipment/return state is separate. Close fields are a queryable projection of the latest closure event and do not replace independent shipment/return states.
- **order_items** (stable line identities): id, order_id FK, line_key CHAR(36) UNIQUE, created_at. No authoritative mutable product/quantity/price fields. Order revision items hold complete snapshots and reference this identity so returns and shipments can refer to a line across revisions. A newly added line receives a new identity; removed lines remain for history.
- **order_revisions**: id, order_id FK, revision_no INT UNSIGNED, revision_type VARCHAR(24), status VARCHAR(24) (`draft`,`pending_customer`,`approved`,`rejected`,`expired`,`superseded`,`applied`,`cancelled`), change_summary TEXT, currency CHAR(3), subtotal/discount_total/customer_shipping_charge/tax_total/grand_total DECIMAL(19,4), proposed_by FK users, proposed_at DATETIME(6), expires_at/decided_at/applied_at DATETIME(6) NULL, idempotency_key VARCHAR(120) NULL UNIQUE, created_at; UNIQUE(order_id,revision_no). Revision 1 is checkout snapshot. Pending revision content is immutable; changes require a new revision.
- **order_revision_items**: id, order_revision_id/order_item_id FKs, line_no INT UNSIGNED, product_id FK products NULL, variant_id FK product_variants NULL, sku_snapshot VARCHAR(80), product_name_snapshot VARCHAR(220), variant_snapshot JSON NULL, product_image_path_snapshot VARCHAR(500) NULL, quantity DECIMAL(18,3), regular_unit_price_snapshot/sale_unit_price_snapshot DECIMAL(19,4) (sale nullable), charged_unit_price/discount_amount/tax_amount/line_total DECIMAL(19,4), currency CHAR(3), tax_snapshot JSON NULL, UNIQUE(order_revision_id,line_no), UNIQUE(order_revision_id,order_item_id). `charged_unit_price` is sale price when one is active, otherwise regular price; line_total is quantity × charged_unit_price, and discount_amount is the line's total difference from regular price. Snapshot both displayed prices so old orders retain what the customer saw. Catalog links are references only and may be nulled only where snapshots remain.
- **order_revision_addresses**: id, order_revision_id FK, address_type VARCHAR(12), recipient_name VARCHAR(160), phone VARCHAR(32), country_code CHAR(2), governorate/city VARCHAR(120), district VARCHAR(120) NULL, street VARCHAR(255), building/floor/apartment VARCHAR(80) NULL, landmark VARCHAR(255) NULL, postal_code VARCHAR(20) NULL, created_at; UNIQUE(order_revision_id,address_type). Captures shipping and billing address for each version.
- **customer_approvals** (decision audit): id, order_revision_id/customer_id FKs, decision VARCHAR(16) (`approved`,`rejected`), decided_at DATETIME(6), channel VARCHAR(24), evidence JSON NULL, idempotency_key VARCHAR(120) UNIQUE, created_at. Each decision references exact revision. Attempts can be logged; one effective terminal decision per revision is app-enforced. Expiration is a system transition, not customer approval.

## Payments, shipping and finance
- **payments**: id, order_id FK, payment_number VARCHAR(40) UNIQUE, method VARCHAR(32) (`cod`,`instapay`), status VARCHAR(24), amount DECIMAL(19,4), currency CHAR(3), provider VARCHAR(80) NULL, timestamps. COD is the only website checkout method. InstaPay is allowed only for staff-entered social orders; enforce channel/method compatibility in application logic.
- **payment_transactions**: id, payment_id FK, transaction_uuid CHAR(36) UNIQUE, transaction_type/status VARCHAR(24), amount DECIMAL(19,4), currency CHAR(3), provider_reference VARCHAR(190) NULL, idempotency_key VARCHAR(120) NULL UNIQUE, request_payload/response_payload JSON NULL, occurred_at DATETIME(6), created_at.
- **payment_proofs**: id, payment_transaction_id FK, storage_path VARCHAR(500), file_sha256 CHAR(64) NULL, submitted_by FK users, submitted_at DATETIME(6), review_status VARCHAR(20) (`pending`,`accepted`,`rejected`), reviewed_by FK users NULL, reviewed_at DATETIME(6) NULL, rejection_reason VARCHAR(255) NULL, created_at. Store image outside public web root; acceptance is a staff decision and does not happen from image upload alone.
- **shipping_companies**: id, code VARCHAR(60) UNIQUE, name VARCHAR(160), integration_driver VARCHAR(80) NULL, config JSON NULL (secrets encrypted/external), is_active, timestamps.
- **shipments**: id, shipment_number VARCHAR(40) UNIQUE, order_id/shipping_company_id FKs (company nullable for manual carrier), leg_type VARCHAR(24) (`outbound`,`return_to_sender`,`customer_return`,`exchange`), status VARCHAR(24), tracking_number VARCHAR(120) NULL, customer_shipping_charge DECIMAL(19,4), carrier_cost_actual DECIMAL(19,4) NULL, expected_cod_collection DECIMAL(19,4), actual_cod_collected DECIMAL(19,4) NULL, currency CHAR(3), shipped_at/delivered_at DATETIME(6) NULL, recipient_snapshot JSON, created_by FK users NULL, timestamps. Customer charge, carrier cost and COD are separate; actual carrier cost may be unknown until invoice/settlement. Record each return-to-sender/failed-delivery transport leg and its carrier cost separately; do not assume customer shipping fee covers it. Shipment actual collection is the latest operational report; statement actual on settlement line is the reconciled carrier evidence. **shipment_items**: id, shipment_id/order_item_id FKs, quantity DECIMAL(18,3), UNIQUE(shipment_id,order_item_id).
- **shipment_events**: id, shipment_id FK, status VARCHAR(24), event_at DATETIME(6), description VARCHAR(500) NULL, location VARCHAR(190) NULL, source VARCHAR(24), provider_event_id VARCHAR(190) NULL, payload JSON NULL, actor_user_id FK users NULL, created_at. Preserve actor for manual updates and source/provider IDs for imported events.
- **carrier_settlements**: id, settlement_number VARCHAR(40) UNIQUE, shipping_company_id FK NULL, status VARCHAR(24), currency CHAR(3), expected_cod_total/actual_collected_total/customer_shipping_charge_total/carrier_cost_total/fees_total/deductions_total/net_due/remitted_total DECIMAL(19,4), statement_reference VARCHAR(120) NULL, period_start/period_end DATE NULL, received_at DATETIME(6) NULL, created_by FK users, timestamps. Header totals reconcile to statement lines and remittances. Proposed cash math: net_due = actual_collected_total - carrier_cost_total - fees_total - deductions_total plus/minus explicit adjustments; approve contract-specific interpretation before implementation.
- **carrier_settlement_items**: id, carrier_settlement_id/shipment_id FKs, expected_cod DECIMAL(19,4), actual_collected DECIMAL(19,4), customer_shipping_charge DECIMAL(19,4), carrier_cost DECIMAL(19,4), carrier_fee DECIMAL(19,4), other_deductions DECIMAL(19,4), net_due DECIMAL(19,4), remitted_amount DECIMAL(19,4), variance_amount DECIMAL(19,4), variance_reason VARCHAR(255) NULL, explained_by FK users NULL, explained_at DATETIME(6) NULL, created_at; UNIQUE(carrier_settlement_id,shipment_id). Proposed variance = expected COD - actual collection; sign convention must be fixed in implementation. Customer shipping charge is not carrier cost.
- **carrier_remittances**: id, carrier_settlement_id/cash_account_id/cash_transaction_id FKs, amount DECIMAL(19,4), currency CHAR(3), reference VARCHAR(120) NULL, remitted_at DATETIME(6), created_by FK users, created_at. Multiple and partial remittances supported; remitted_total is a projection. A remittance is one cash receipt.
- **carrier_remittance_items**: id, carrier_remittance_id FK, carrier_settlement_item_id FK, amount DECIMAL(19,4), currency CHAR(3), created_at; UNIQUE(carrier_remittance_id,carrier_settlement_item_id). Maps partial remittances to shipments; allocations sum to remittance amount and settlement-item remitted amount.
- **carrier_settlement_adjustments**: id, carrier_settlement_id FK, carrier_settlement_item_id FK NULL, adjustment_type VARCHAR(24), amount DECIMAL(19,4) signed, currency CHAR(3), reason VARCHAR(255), created_by FK users, reverses_adjustment_id FK self NULL, created_at. Append-only correction after statement reconciliation; never overwrite settled line/header facts.
- **returns**: id, return_number VARCHAR(40) UNIQUE, order_id/customer_id FKs, case_type VARCHAR(20) (`return`,`exchange`), status, reason_code VARCHAR(80), reason TEXT NULL, requested_at DATETIME(6), received_at NULL, resolution VARCHAR(24) NULL, notes TEXT NULL, created_by FK users NULL, timestamps. **return_items**: id, return_id/order_item_id FKs, quantity DECIMAL(18,3), condition VARCHAR(24) NULL (`sellable`,`damaged`,`defective`,`missing`), disposition VARCHAR(24) NULL (`customer_refund`,`replacement`,`no_refund`,`other`), refund_amount DECIMAL(19,4), replacement_order_item_id FK order_items NULL, timestamps. Inspection records returned, defective and damaged units separately; inventory is outside this schema. Link refunds and damage costs to immutable financial/order-cost entries. A defect exchange is a post-delivery service case, not automatically a failed original order; replacement order and price/shipping difference policy remain open.
- **refunds**: id, refund_number VARCHAR(40) UNIQUE, return_id/payment_id FK NULL, order_id FK, status, amount DECIMAL(19,4), currency CHAR(3), reason VARCHAR(255) NULL, refunded_at NULL, created_by FK users, timestamps.
- **expenses**: id, expense_number VARCHAR(40) UNIQUE, expense_type VARCHAR(24) (`order_operating`,`general_overhead`,`other`), cost_category VARCHAR(32) (`inbound_delivery`,`carrier_shipping`,`packaging`,`advertising`,`other`) NULL, description VARCHAR(255), amount DECIMAL(19,4), currency CHAR(3), expense_date DATE, order_id FK orders NULL (direct attribution only), status, created_by FK users, timestamps. Factory/product cost is stored in product price history and order cost snapshots; no supplier payable/receipt cost ledger is included. Shared advertising is not allocated to specific orders without an approved attribution rule.
- **order_cost_entries** (append-only cost snapshots): id, order_id FK, order_item_id FK NULL, shipment_id FK shipments NULL, cost_type VARCHAR(32) (`product`,`inbound_delivery`,`carrier_shipping`,`packaging`,`advertising`,`other`), amount DECIMAL(19,4), currency CHAR(3), basis VARCHAR(16) (`estimate`,`actual`),  expense_id FK NULL, recorded_at DATETIME(6), recorded_by FK users, reverses_entry_id FK self NULL, notes TEXT NULL, created_at. Product cost may attach to an item; actual outbound/return-to-sender/failed-delivery carrier costs link to the shipment leg. Estimate/actual/reversal remain auditable; never count estimate and actual for the same cost.
- **expense_cash_allocations**: id, expense_id/cash_transaction_id FKs, amount DECIMAL(19,4), currency CHAR(3), created_at; UNIQUE(expense_id,cash_transaction_id). Supports partial/multiple disbursements without a circular expense-to-cash FK.
- **cash_accounts**: id, code VARCHAR(60) UNIQUE, name VARCHAR(160), account_type VARCHAR(24), currency CHAR(3), is_active, timestamps.
- **cash_sessions**: id, cash_account_id/opened_by/closed_by FKs (closer nullable), opening_balance/closing_count/expected_balance DECIMAL(19,4), opened_at DATETIME(6), closed_at NULL, notes TEXT NULL.
- **cash_transactions**: id, cash_account_id/cash_session_id FKs (session nullable), transaction_number VARCHAR(40) UNIQUE, direction VARCHAR(8), transaction_type VARCHAR(32), amount DECIMAL(19,4), currency CHAR(3), source_type VARCHAR(50) NULL, source_id BIGINT UNSIGNED NULL, occurred_at DATETIME(6), created_by FK users, reversal_of_id self-FK NULL, description VARCHAR(255) NULL, created_at. Append-only.


## Marketing, content and audit
- **homepage_sections**: id, code VARCHAR(80) UNIQUE (predefined template section key), section_type VARCHAR(32), product_collection_id FK product_collections NULL, banner_placement VARCHAR(80) NULL, sort_order INT, is_enabled TINYINT(1), settings JSON NULL (validated according to section_type), created_by/updated_by FK users NULL, timestamps. Lets dashboard staff enable/disable and reorder supported home-page sections; it is not a free-form page builder. `home_testimonials` uses `settings.testimonials` for curated slider entries (UUID, public image path, sort order, active flag, and required Arabic/English name and message); dashboard changes are written to `activity_logs`.
- **homepage_section_translations**: id, homepage_section_id FK, locale VARCHAR(10), heading VARCHAR(220) NULL, subheading VARCHAR(500) NULL, body TEXT NULL, UNIQUE(homepage_section_id,locale). Store only localized display text; do not allow arbitrary HTML.
- **coupons**: id, code VARCHAR(80) UNIQUE, discount_type VARCHAR(16), discount_value DECIMAL(19,4), currency CHAR(3) NULL, minimum_order_amount/maximum_discount DECIMAL(19,4) NULL, usage_limit/per_customer_limit INT UNSIGNED NULL, starts_at/ends_at NULL, is_active, timestamps.
- **coupon_usages**: id, coupon_id/customer_id/order_id FKs, discount_amount DECIMAL(19,4), currency CHAR(3), used_at DATETIME(6), UNIQUE(coupon_id,order_id).
- **banners**: id, placement VARCHAR(80) (including homepage design slots), image_path VARCHAR(500), target_url VARCHAR(500) NULL, sort_order INT, starts_at/ends_at DATETIME(6) NULL, is_active TINYINT(1), created_by/updated_by FK users NULL, timestamps. **banner_translations**: id, banner_id FK, locale, title/alt_text VARCHAR(255) NULL, UNIQUE(banner_id,locale). Dashboard users manually upload/replace, activate/deactivate and order homepage images; visibility is filtered by placement, active flag and schedule. Archive/deactivate instead of deleting a banner with history.
- **cms_pages**: id, slug VARCHAR(190) UNIQUE, status, published_at NULL, created_by/updated_by FKs users, timestamps. **cms_page_translations**: id, cms_page_id FK, locale, title VARCHAR(220), body LONGTEXT, meta_title VARCHAR(220) NULL, meta_description VARCHAR(500) NULL, UNIQUE(cms_page_id,locale).
- **about_faqs**: id, is_active TINYINT(1), sort_order INT, created_by/updated_by FK users NULL, timestamps, deleted_at NULL. **about_faq_translations**: id, about_faq_id FK, locale VARCHAR(10), question VARCHAR(500), answer TEXT, created_at/updated_at, UNIQUE(about_faq_id,locale). Dashboard staff manage each About page question and answer, Arabic/English text, visibility and order. Deactivate/archive rather than hard-delete a FAQ already shown to customers.
- **settings**: id, group VARCHAR(80), key VARCHAR(120), value JSON, is_public TINYINT(1), timestamps, UNIQUE(group,key); never plaintext secrets.
- **order_activity_events** (append-only): id, order_id FK, actor_user_id FK users NULL (NULL reserved for system), event_type VARCHAR(32) (`created`,`status_changed`,`follow_up`,`assigned`,`closed`,`reopened`,`note_added`), previous_status/current_status VARCHAR(24) NULL, close_outcome VARCHAR(16) NULL (`success`,`failure`), reason_code VARCHAR(80) NULL, details JSON NULL, next_follow_up_at DATETIME(6) NULL, occurred_at DATETIME(6), idempotency_key VARCHAR(120) NULL UNIQUE, created_at. Record creator, every status change, follow-up/assignment, closure and reopening with actor and time. Never edit/delete events; correct mistakes with a compensating event. Closure outcome/reason is copied to the order projection in the same transaction.
- **activity_logs**: id, actor_user_id FK NULL, event VARCHAR(120), subject_type VARCHAR(80), subject_id BIGINT UNSIGNED, before/after JSON NULL, ip_address VARCHAR(45) NULL, user_agent VARCHAR(500) NULL, correlation_id CHAR(36) NULL, created_at. Immutable, redact secrets/needless personal data. Use for general dashboard audit; order-specific lifecycle events also go to `order_activity_events`.
- **product_reviews**: id, product_id FK, customer_id FK, order_item_id FK order_items NULL, rating TINYINT UNSIGNED, comment TEXT NULL, moderation_status VARCHAR(20) (`pending`,`approved`,`rejected`), visibility_status VARCHAR(16) (`visible`,`hidden`), submitted_at DATETIME(6), reviewed_by FK users NULL, reviewed_at DATETIME(6) NULL, rejection_reason VARCHAR(255) NULL, timestamps. Dashboard admin approves/rejects and controls visibility; only approved + visible reviews appear publicly. Hiding an approved review does not erase its moderation decision or history. Verified-purchase requirement remains open; if required, order_item_id becomes NOT NULL and ownership/order-product match is app-validated.
- **customer_feedback**: id, feedback_number VARCHAR(40) UNIQUE, customer_id FK NULL, order_id FK NULL, sender_name_snapshot VARCHAR(160) NULL, sender_email_snapshot VARCHAR(190) NULL, feedback_text TEXT, moderation_status VARCHAR(20) (`pending`,`approved`,`rejected`), visibility_status VARCHAR(16) (`visible`,`hidden`), show_on_homepage TINYINT(1), submitted_at DATETIME(6), reviewed_by FK users NULL, reviewed_at DATETIME(6) NULL, staff_note TEXT NULL, timestamps. This is general feedback about the store/service, distinct from product reviews and support tickets. Dashboard admin approves/rejects each submission and controls whether approved feedback is visible on the website and/or homepage. Hidden feedback remains stored in the dashboard; customer-facing identity display policy remains open.
- **contact_messages**: id, customer_id FK NULL, sender_name VARCHAR(160), email VARCHAR(190) NULL, phone VARCHAR(32) NULL, subject VARCHAR(220) NULL, message TEXT, status VARCHAR(20) (`new`,`read`,`converted`,`closed`,`spam`), received_at DATETIME(6), handled_by FK users NULL, handled_at DATETIME(6) NULL, converted_ticket_id FK support_tickets NULL, timestamps. Public Contact Us submissions can be from guests; preserve sender/contact snapshots if customer account changes.
- **support_tickets**: id, ticket_number VARCHAR(40) UNIQUE, customer_id FK NULL, order_id FK NULL, subject VARCHAR(220), status VARCHAR(24) (`open`,`in_progress`,`waiting_customer`,`resolved`,`closed`), priority VARCHAR(16), category VARCHAR(60) NULL, assigned_to FK users NULL, requester_name/email/phone snapshots, opened_at DATETIME(6), first_response_at/resolved_at/closed_at DATETIME(6) NULL, timestamps. Keep support status independent from order status; ticket may be opened by guest or attached to an order.
- **support_ticket_messages**: id, support_ticket_id FK, sender_type VARCHAR(16) (`customer`,`staff`,`system`), customer_id FK NULL, staff_user_id FK users NULL, visibility VARCHAR(16) (`public`,`internal`), body TEXT, sent_at DATETIME(6), edited_at DATETIME(6) NULL, created_at. Customer-facing replies are public; internal notes are never exposed to the customer. Prefer append-only corrections rather than editing sent messages.
- **support_ticket_attachments**: id, support_ticket_message_id FK, storage_path VARCHAR(500), original_name VARCHAR(255), mime_type VARCHAR(120), byte_size BIGINT UNSIGNED, file_sha256 CHAR(64) NULL, uploaded_at DATETIME(6). Store outside public web root and validate type/size.
- **support_ticket_events** (append-only): id, support_ticket_id FK, actor_user_id FK users NULL, event_type VARCHAR(32) (`created`,`status_changed`,`assigned`,`priority_changed`,`resolved`,`reopened`), previous_value VARCHAR(120) NULL, new_value VARCHAR(120) NULL, details JSON NULL, occurred_at DATETIME(6), created_at. Enables dashboard/customer timeline and staff accountability without overloading general logs.

### Reporting model
No separate mutable weekly/monthly/yearly totals table is required for the first schema. Derive reports from immutable order revisions/approvals, payments/transactions, shipment records, returns/refunds and append-only order cost entries, using an explicit report date basis. If later snapshots are needed for speed, each run must record its period, basis/version and generation time and be reproducible from those source ledgers. Never join historical orders to current product price or current product text to calculate old sales.
