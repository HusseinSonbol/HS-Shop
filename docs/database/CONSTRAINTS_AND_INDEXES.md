# Constraints, indexes and integrity

## Referential actions
Use InnoDB FKs and RESTRICT by default. Never cascade-delete orders, revisions, payments, shipments, returns/refunds, cash, expenses, supplier master records referenced by product options or order selections, or audit history. Archive suppliers and catalog entities. Supplier deletion is blocked while product options or order selections reference it; unlinking is an explicit catalog change, while prior order selections retain snapshots. Existing sessions deliberately have no users FK. Correct posted financial facts with linked reversal/compensating rows, not deletion. There are no procurement, inventory, or stock tables in the current scope.

## Unique constraints
Enforce every UNIQUE/composite key listed in [TABLES.md](TABLES.md): user email; customer user_id/number; role/permission codes and pivots; entity+locale translations; category/brand/product slugs; supplier code; unique product-supplier pair and supplier-history version; product/variant SKU and optional barcode; attribute code and attribute/value code; variant+attribute/value; product price-history version; all document numbers; cart+variant and customer+product favorite; order+revision number; revision+line identity/number; settlement+shipment; remittance+statement line; coupon code and coupon+order; CMS slug; FAQ+locale; settings group+key; Laravel UUIDs/idempotency references. MySQL permits multiple NULLs in unique indexes. Effective customer decision uniqueness is a locked application invariant because rejected/duplicate attempts may be audited.

## Same-row checks and application-level invariants
Where the supported MySQL version enforces CHECK constraints, use them for nonnegative amounts/quantities where appropriate and valid time ranges. DECIMAL is mandatory for money. MySQL constraints alone cannot enforce the following cross-row rules; validate them in application transactions and lock the affected rows:

1. Products may link to multiple active supplier options, but each option pair is unique. A supplier selection for an order line must reference a supplier linked to that line’s product and be active/available at selection time; capture unit cost, currency, supplier name, actor and timestamp. Re-selection appends a new event and cannot rewrite old choices.
2. A product has the correct default variant cardinality; selected attribute values belong to the same attribute; enforce at most one default image, variant, category and address under concurrency.
3. Revision totals equal line/discount/shipping/tax totals. Changed price/product/quantity cannot be fulfilled before approval of the exact current revision. Pending revisions are immutable; decisions, expiry and supersession lock the order/revision.
4. Order item product/variant identity and currency agree with their customer-facing snapshots; supplier selection history remains separate and immutable. Historical snapshots are never rebuilt from current catalog values.
5. Guest browsing/cart/checkout viewing is allowed, but website order placement requires a linked active customer user. Preserve guest cart and checkout choices through registration/login, then transactionally attach/merge the cart and revalidate current availability/prices before placing the order. Customer addresses are persisted only after account identity is established. Rotate the session identifier after authentication and never authorize cart access using a client-controlled cart ID alone. Social orders may use a staff-created customer. Website orders allow COD only; InstaPay is valid only for staff-entered Facebook/Instagram orders. Proof upload alone is not payment verification.
6. Customer return quantities cannot exceed delivered quantities less prior accepted returns. Refunds cannot exceed eligible amounts less prior refunds. Return/damage records do not update inventory because no inventory ledger exists.
7. A shipment's item quantities cannot exceed unshipped order quantities across shipments. Carrier settlement totals reconcile to lines; remittance allocations reconcile and cannot exceed net due absent approved exception. Statement corrections are append-only adjustments.
8. Order cost source, order, product line and currency must agree. An actual cost supersedes/reverses its estimate in reporting, while both remain auditable. Product acquisition cost remains separate from operating costs. Shared advertising is not allocated without an approved rule.
9. Coupon limits and address-default uniqueness are concurrency-safe. Order transitions follow the owner-approved sequential `new` → `confirmed` → `shipped` → `received` workflow; `received` is successful terminal state after staff confirms customer receipt. Failure closure is a separate projection that leaves status unchanged; block further transitions until reopened. Enforce under a row lock.
10. Polymorphic cash/activity source references cannot have ordinary FKs; validate source type/existence and prohibit deletion.
11. Order creator, status changes, follow-up, assignment, closure and reopening append immutable events with actor/time and previous/current values. Failure closure requires an approved reason code (and explanatory text for `other`); successful closure is the transition to `received` and requires recorded customer-receipt confirmation. Reopening clears the failure projection without changing operational status and never erases prior closure events; the mutable `orders` closure columns are only the current projection. A single follow-up form accepts optional assignment, date and note; append events only for submitted changes.
12. Curated collection membership/order is manually managed, not derived from product creation or sales. Homepage image placement/order/schedule is valid and audited.
13. Support-ticket internal notes and private attachments are never exposed in customer views. Ticket assignments/state changes append events.
14. Calendar reports use `Africa/Cairo`; months start on day 1 and weeks run Saturday-Friday. Revenue/return recognition dates and percentage denominators remain explicit business decisions.
15. Product price history preserves every cost input, profit rate and published price version. Supplier-specific costs are separately historized and the selected supplier cost is snapshotted per order line. Do not recalculate historical orders from current prices.
15a. A sale price, when present, must be positive and lower than the regular price for the same variant; enforce with a CHECK where supported and validate in application code. Only an administrator with price-management permission may change a variant's regular/sale price; record actor, timestamp, reason, and append a new history version. In an order revision, `charged_unit_price` equals the active sale price or else the regular price; line_total = quantity × charged_unit_price; line discount = quantity × (regular price - charged unit price), never negative. Revision snapshots preserve regular price, optional sale price, charged unit price and discount. Price updates never rewrite past revisions. Sale scheduling or automatic expiry is not implied.
16a. Product-level availability is only `available` or `unavailable` and gates all its variants in the storefront; it is not inventory. Supplier option availability is maintained independently. Each manual product availability change appends an actor/time history row.
16. In-dashboard notifications are persisted and permission-scoped; no realtime delivery behavior is implied.
17. Homepage sections must use supported section types; JSON settings are validated by type, localized text is escaped, and enabled sections have deterministic order. The dashboard cannot store arbitrary executable HTML.
18. Product reviews and general customer feedback are distinct. Admin approval/rejection and visibility are separate: only `moderation_status=approved` and `visibility_status=visible` may be shown publicly. `show_on_homepage=1` additionally selects approved, visible customer feedback for the homepage. Hiding content must not erase it; every moderation and visibility change is recorded in `activity_logs`.

## Circular foreign keys
`orders.applied_revision_id` and `order_revisions.order_id` form a circular relationship. Create the order with a nullable pointer, insert revision 1, then set the pointer in the same transaction; add the pointer FK after both tables exist. `product_variants.current_price_version_id` and `product_price_history.product_variant_id` form a similar cycle; create variant, append initial price history, and update the pointer atomically.

## Concurrency and durability
Use transactions and `SELECT ... FOR UPDATE` on order/revision, coupon, payment, return/refund, carrier settlement/remittance and cash session before conditional updates. No inventory/receipt/procurement locks are applicable in this scope. Keep external calls outside long SQL transactions; persist idempotency intent and reconcile uncertain timeouts before retry. Define consistent lock order and safe deadlock retries. MySQL has no partial unique index; active-only uniqueness needs locked application logic or an approved generated-column approach.
