# HS Shop known risks

This register reflects the current planning/repository state. Risks are not proof of an active vulnerability; they identify issues to resolve or control before the affected feature ships.

| Risk | Impact | Current status / mitigation |
|---|---|---|
| MySQL is the approved application target, while automated feature tests use in-memory SQLite. | MySQL-specific constraints, JSON, locking, decimal arithmetic, and migrations may differ; SQLite tests alone can miss production defects. | `.env.example` selects MySQL. Run migrations and concurrency-sensitive acceptance checks against the deployment-equivalent MySQL version before release. |
| The database proposal is much broader than the fast MVP. | Implementing every documented module up front delays launch and increases migration complexity. | Follow `docs/IMPLEMENTATION_PLAN.md`; defer warehouses, full settlements/reconciliation, and shipping integrations. Keep only MVP-required records and extension points. |
| The per-unit advertising input may not reflect shared campaign spend. | A displayed product markup rate can be mistaken for realized or accounting profit when campaign costs are shared across products. | Markup basis and four-decimal half-up percentage rounding are approved; regular price remains manually set. Treat advertising input as a per-unit estimate and keep campaign allocation/reporting and accounting profit policy open. |
| Tax, refund eligibility, damaged-stock valuation, and accounting profit policy remain open. | Reports or refunds could be misleading or violate intended business policy. | Show component amounts separately; do not claim statutory/accounting net profit or automate unresolved refunds/write-offs. |
| Report event-date and KPI definitions remain open. | Orders, delivery, collections, refunds and returns can land in different periods; percentages can be misinterpreted. | Use confirmed Cairo calendar boundaries; label the date basis and show counts/amount denominators until definitions are approved. |
| New routes may regress authentication, staff authorization, customer ownership checks or rate limits as the MVP expands. | A missed server-side check could expose customer or operational data. | Current customer/admin authentication, permissions, ownership checks and endpoint throttles exist for implemented workflows; keep authorization and abuse-case tests with every new workflow and repeat the route review before release. |
| Transfer proof images, review/support attachments and contact data are sensitive. | Publicly exposed uploads or over-retained personal data can harm customers. | Store private uploads outside public root, validate content/size, authorize downloads, minimize logs, and resolve retention policy before release. |
| Static eMarket reference assets remain in the repository. | Accidental reuse could reintroduce demo content or Bootstrap 3 into the current storefront. | Active routes use the Rapidshop Bootstrap 5 layout; S2-11 removed the live eMarket demo route/view/layout. Keep reference assets out of active views and confirm any redistribution/license requirements before publishing them. |
| Automated feature tests use SQLite and do not yet cover the complete customer storefront journey. | Passing current tests does not establish MySQL concurrency behavior or end-to-end cart, checkout, account and review submission behavior. | Focused review/feedback submission tests now cover permissions, eligibility, moderation defaults and duplicate review rejection. Verify locking on MySQL and complete the end-to-end storefront journey before release. The owner approved public display of a guest's submitted name only after moderation and visibility approval. |
| Production infrastructure has not been inspected. | A development `.env`, missing backups, or HTTP deployment could expose data or prevent recovery. | Before deployment set production environment values (`APP_DEBUG=false`, HTTPS URL and secure cookies), configure database/storage backups and prove a restore. These runtime settings cannot be verified from this local source review. |
| Responsive layouts and supported browser versions have not had manual device/browser acceptance. | Breakpoint CSS and a successful asset build do not prove touch behavior or visual correctness across supported browsers. | Bootstrap 5 layouts include mobile breakpoints and viewport metadata; test the agreed phone/tablet and browser matrix on a staging site before launch. |
| Exchange/refund/failed-delivery treatment is not fully specified. | Duplicate shipping charges, incorrect order closure, or double-counting losses are possible. | Keep delivery legs, exchange cases, refunds and costs as distinct records; approve rules before automating settlement or customer liability. |

## Release blockers by feature

- **Price and profitability reporting:** shared advertising attribution, event-date/KPI denominators, and accounting treatment remain open; distinguish displayed markup from realized/accounting profit.
- **Automatic refund/accounting results:** refund policy, tax treatment and accounting treatment.
- **Authoritative profit/KPI percentages:** event date, denominators, damaged-stock valuation, and shared-cost treatment.
- **Production data handling:** retention/anonymization and final database/deployment strategy.
- **Support operations:** service levels, retention, closure/reopen policy, guest reply channel and escalation are unresolved. Staff access is permission-gated; notification delivery is saved in-dashboard and non-realtime only.
